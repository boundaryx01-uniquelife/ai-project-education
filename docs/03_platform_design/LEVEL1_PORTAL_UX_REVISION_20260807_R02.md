## 사용자 검토에서 확인된 문제

1. 화면이 항목 나열 중심이라 에이전트를 만드는 활동이라는 목적이 즉시 보이지 않았다.
2. 시작 시 만들고자 하는 목표를 잡는 흐름이 약했다.
3. 에이전트 제작 방법을 배우는 것인지 실제 에이전트를 제작하는 것인지 구분이 어려웠다.
4. 생성형 AI에 무엇을 보내고 그 결과를 어떻게 다음 활동에 반영하는지 직관적이지 않았다.
5. 한 화면에 정보가 많고 현재 봐야 할 곳과 완료 확인 위치가 약했다.
6. 시작 화면에서 최종 결과물의 모습을 먼저 보여줄 필요가 있었다.

## R02 UX 원칙

### 1. 결과를 먼저 보여준다

첫 화면 최상단에서 완성 예시 에이전트의 `입력 → 처리 → 출력` 모습을 보여준다.

### 2. 목표를 먼저 잡는다

첫 화면에서 다음 세 질문에 답하게 한다.

- 누가 사용할까?
- 무슨 문제를 해결할까?
- 무엇을 받게 할까?

상세 DEFINE은 다음 단계에서 구체화한다.

### 3. 실제 제작 활동임을 명확히 한다

상단 설명을 `생성형 AI와 주고받으며 내 미니 에이전트 만들기`로 바꾸고, 최종 산출물이 `에이전트 카드 + 실행 패키지`임을 명시한다.

### 4. AI 상호작용을 한 가지 반복 루프로 보여준다

모든 단계에서 같은 패턴을 사용한다.

`작성 → AI에 보낼 내용 복사 → 생성형 AI에서 실행 → 결과 확인·반영 → 완료 확인`

`Context Packet`은 보조 용어로만 두고 기본 화면 이름은 `지금 AI에게 보낼 내용`으로 한다.

### 5. 한 화면의 초점을 하나로 줄인다

기존 3열 구조를 제거하고 `단계 메뉴 + 현재 작업` 2열로 단순화한다.

- 예시는 접어서 필요할 때만 연다.
- State Snapshot, 교사용 점검, 산출물 미리보기도 보조 영역으로 접는다.
- 현재 단계의 실제 입력과 AI 교환 흐름을 중앙에 둔다.

### 6. 완료 확인을 강하게 강조한다

각 단계 하단에 노란색 강조 박스로 `마지막으로 여기만 확인` 영역을 고정한다.

## 사용자에게 보이는 단계명

내부 생명주기 명칭은 유지하지만 학습자 화면은 다음처럼 표시한다.

1. 완성 모습 먼저 보기
2. 목표 정하기
3. 근거 넣기
4. 작동 방식 만들기
5. 에이전트 만들기
6. AI로 시험하기
7. 완성본 받기
8. 개선하기

## 유지하는 내부 기준

- DEFINE → COLLECT → STRUCTURE → BUILD → TEST → PUBLISH → IMPROVE 생명주기는 변경하지 않는다.
- 자료 3건, 처리 단계 4개 이상, 정상·경계·실패 테스트의 최소 게이트는 유지한다.
- AI API, 로그인, DB는 추가하지 않는다.
- 사람의 최종 판단 원칙을 유지한다.

## 검증 상태

UX 수정은 브랜치 `feature/stage-03-level-1-portal`에 반영한다.

실제 브라우저에서 다음을 다시 확인한 뒤 병합 여부를 판단한다.

- 처음 10초 안에 무엇을 만드는 화면인지 이해되는가
- 완성 예시를 보고 목표를 바로 입력할 수 있는가
- 현재 단계에서 어디를 작성해야 하는지 보이는가
- 생성형 AI에 보낼 버튼이 즉시 보이는가
- 단계 종료 시 완료 확인 영역을 놓치지 않는가
- BUILD/PUBLISH에서 실제 에이전트가 만들어졌다는 느낌이 드는가
