## 변경 이유

이전 화면은 MVP를 만드는 세부 입력을 여러 단계로 나눠 반복하게 했고, MVP 이후 실제 에이전트 품질을 높이는 수정·검증·배포 판단이 약했다.

또한 왼쪽 샘플이 단순 입력 폼 수준이라 학습자가 만들고 싶은 결과의 매력을 충분히 느끼기 어려웠다.

## 학습자용 4단계

### 1. MVP 제작

목표와 최소 입력을 정한 뒤 지금 바로 시험 가능한 첫 작동 버전을 만든다.

- 사용자
- 해결할 문제
- 원하는 결과
- 꼭 필요한 입력

내부적으로 DEFINE → COLLECT → STRUCTURE → BUILD를 압축해 수행한다.

### 2. 수정·제약

MVP를 직접 써보고 문제가 생긴 부분을 수정한다.

특히 다음을 명시한다.

- 반드시 해야 할 일
- 절대 하지 말아야 할 일
- 정보가 부족할 때 다시 질문할 조건
- 실패하거나 판단할 수 없을 때의 행동

에이전트 품질은 기능 추가보다 제한·금지·재질문 규칙의 명확성에서 크게 달라질 수 있음을 경험하게 한다.

### 3. 검증

검증을 두 갈래로 분리한다.

- 사용자 검증: 실제 사용자가 써보고 불편, 오답, 누락 조건을 확인
- AI 검증: 모호한 입력, 조건 충돌, 잘못된 정보, 무리한 요청 등 실패 가능성을 공격적으로 탐색

정상 작동 확인만으로 검증을 끝내지 않는다.

### 4. 배포 판단

이를 '완성'으로 부르지 않는다.

현재 결과를 기준으로 다음 개발 단계의 범위를 결정한다.

- 로컬 또는 웹
- 개인 사용 또는 공유
- 결과·사용자 데이터 저장 필요 여부
- 데이터베이스 필요 여부
- 날씨·가격·지도·검색 등 외부 API 필요 여부

판단 결과에 따라 로컬/채팅형 유지, 정적 웹, 웹+DB, 외부 API 연동 중 필요한 수준만 선택한다.

## 화면 원칙

- 왼쪽 SAMPLE / 오른쪽 FOLLOW
- 왼쪽 상단에는 단순 설명이 아니라 실제 조작 가능한 제품형 미니 프리뷰 배치
- 오른쪽은 현재 단계 입력만 표시
- 각 단계에서 WEB 활동과 AI 활동을 시각적으로 분리
- 이전 단계의 목표·입력은 다시 작성하지 않음
- 보조 설명은 details로 접음
- 마지막 단계는 '완성'이 아니라 '다음 개발 방향 결정'

## 내부 공통 생명주기와 관계

프로젝트의 공통 생명주기 `DEFINE → COLLECT → STRUCTURE → BUILD → TEST → PUBLISH → IMPROVE`는 유지한다.

다만 학습자 화면에서는 실제 제작 경험에 맞춰 이를 4개의 큰 단계로 묶고, 필요하면 TEST와 IMPROVE를 반복한다.

## 현재 상태

브랜치 `feature/stage-03-level-1-portal`에 UX와 로직을 반영했다.

병합 전 실제 브라우저에서 다음을 확인한다.

1. 제품형 미니 프리뷰가 제작 동기를 주는가
2. MVP 단계에서 입력이 충분히 적은가
3. 2단계가 기능 추가보다 금지·제약 설정에 집중되는가
4. 사용자 검증과 AI 검증의 차이가 직관적인가
5. 배포 판단에서 DB/API 필요 여부를 자연스럽게 생각하게 되는가
