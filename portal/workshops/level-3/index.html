Level 3는 외부 데이터가 정상일 때만 작동하는 화면을 만들지 않습니다. 출처·갱신 시각·빈 결과·연결 오류를 함께 다루는 부산 생활 데이터 앱을 만듭니다.

오늘의 결과물교사 중계 주소 → 데이터 요청 → 상태별 결과 화면서비스키는 학생 HTML이나 GitHub Pages에 절대 넣지 않습니다.

STEP 01

부산 생활에서 찾을 정보를 고릅니다.

첫 MVP는 지도·위치 권한보다, 한 가지 검색과 신뢰할 수 있는 결과 상태를 분명하게 보여 주는 데 집중합니다.

다음 행동: AI에게 상태가 있는 결과 화면을 요청합니다.

STEP 02

정상·빈 결과·오류 화면을 함께 요청합니다.

AI에게 API 키나 실제 주소를 넣어 달라고 하지 않습니다. 먼저 예시 데이터로 세 상태를 모두 보이는 화면을 만듭니다.

AI에 보낼 요청
안전 규칙
키는 교사가 관리합니다.
  • HTML·GitHub Pages·화면 캡처에 서비스키를 넣지 않는다.
  • 교사 중계 주소는 정규화된 결과만 돌려준다.
  • 출처와 마지막 갱신 시각을 항상 표시한다.
다음 행동: 샘플 또는 교사 중계 데이터를 확인합니다.


STEP 03
교사 중계 응답을 실제로 확인합니다.
수업용 중계 주소가 준비되어 있으면 조회할 수 있습니다. 주소가 없을 때는 샘플 응답으로 화면의 세 상태를 먼저 연습합니다.
안전한 요청
중계 주소를 넣지 않으면 네트워크 요청은 보내지 않습니다.
응답 형식: { source, updatedAt, arrivals: [{ route, station, minutes }] }
학생이 보는 결과
DATA STATUS
아직 데이터를 요청하지 않았습니다.
정상 결과, 검색 결과 없음, 연결 오류를 각각 확인해 보세요.
다음 행동: 세 가지 상태가 모두 보이는지 검사합니다.


STEP 04
데이터가 없거나 실패할 때도 설명합니다.
외부 데이터는 멈추거나 비어 있을 수 있습니다. 실패를 숨기는 대신 사용자에게 이유와 다음 행동을 알려 주는 것이 Level 3의 완성 기준입니다.
API CONTRACT

중계 주소, 요청 파라미터, 응답 형식, 데이터 출처·갱신 주기를 기록해 공유합니다.
